# Gesamt-Audit Crewplaner — 2026-08-09

Geprüft: Stand v0.6.1 / Hook v4.18, Branch `main`.
Auftrag: Logik, Sinnhaftigkeit, Sicherheit, Schutz vor Codeklau, Codestruktur, Programmierung.

**Art der Prüfung:** anonym gemessen gegen Live **und** Test (kein Superuser-Zugang, rein lesend),
dazu Quelltextprüfung und Mutationstests der bestehenden Guards.
**Ergebnis:** Befund, keine Umsetzung. Nichts am Code geändert — `node tests/run.mjs` steht
vorher wie nachher auf 132 grün.

---

## Zusammenfassung

**3 kritische, 6 wichtige, 5 kosmetische Befunde.**

Die gute Nachricht zuerst, und sie ist echt: **von außen ist nichts offen.** Alle acht
Collections liefern einem Fremden auf beiden Backends null Datensätze. Die Härtungsarbeit
aus v0.5.1–v0.6.1 wirkt nachweislich — das ist mehr, als viele Projekte dieser Größe
vorzuweisen haben.

Die schlechte Nachricht betrifft genau die zwei Dinge, die im Auftrag standen:

1. **Der Live-Server liefert dein komplettes Repository aus** — interne Doku, Server-Hook,
   Infrastrukturdaten, die Chronik aller je gefundenen Lücken. Ohne Anmeldung, mit einem Klick.
2. **Ein einziges Crew-Konto genügt, um den gesamten Personendatenbestand abzuziehen** —
   alle Zuweisungen aller Touren, alle Namen, alle Mailadressen. Und dasselbe Konto kann sich
   selbst Zugriff auf fremde Touren verschaffen.

Beides ist kein Zufallsfund, sondern strukturell: Die Absicherung wurde bisher stets gegen
*anonyme* Zugriffe gebaut. Die Innensicht — was darf jemand, der legitim angemeldet ist —
war nie Gegenstand einer Prüfung.

---

## Was gut ist

Das gehört genauso in den Bericht wie die Mängel:

- **Anonyme Abschottung hält.** `node tools/check-pb-rules.mjs`, 2026-08-09:
  ```
  ── LIVE   assignments 0 · crew_members 0 · users 0 · plans 0 · email_log 0 · activity_log 0
  ── TEST   dieselben Werte
  CORS: eigenes Frontend freigegeben · fremde Herkunft bekommt keine Freigabe
  Ergebnis: alle geprüften Regeln stehen richtig.
  ```
  Beide Instanzen entsprechen exakt dem hinterlegten Soll-Stand.

- **Die Hook-Routen sind sauber gebaut.** `/myplan/{id}` prüft die Berechtigung serverseitig
  und lehnt mit **404 statt 403** ab — verrät also nicht einmal, ob eine Tour existiert. Die
  öffentlichen Routen geben bewusst weder `view_token` noch `owner` noch `crew_email` heraus.
  Das ist handwerklich gut gemacht und kommentiert.

- **Keine Konto-Aufzählung.** Passwort-Reset antwortet für eine existierende und eine
  erfundene Adresse identisch (`204` / `204`).

- **Keine Secrets im Arbeitsstand**, kein `eval`, kein `new Function`.

- **Die Testkultur ist ungewöhnlich stark.** 132 Tests, davon ein Dutzend echte Guards, die
  ganze Fehlerklassen statisch abfangen. Ein Mutationstest hat das bestätigt: Ich habe den
  `view_token` in die `/viewplan`-Antwort geschmuggelt — der Guard wurde sofort rot.

- **Die Dokumentation ist außergewöhnlich.** Jede Entscheidung ist mit Begründung und
  Gegenprobe festgehalten. Das ist der Grund, warum dieses Audit überhaupt so schnell in die
  Tiefe kam. (Dass sie öffentlich im Netz steht, ist der Befund K-1 — nicht ihre Qualität.)

## Kritisch

### K-1 · Das Live-Frontend liefert das komplette Repository aus

**Was ist.** `crewplanner.nyxlightwork.de` serviert nicht nur die App, sondern jede Datei des
Repos. Gemessen am 2026-08-09, alle mit `200`:

| Pfad | Größe | Inhalt |
|---|---|---|
| `/CLAUDE.md` | 164 KB | Container-Name, Volume-Pfad, SSH-Alias, Admin-Adresse, Lückenchronik |
| `/.pb_hooks/main.pb.js` | 48 KB | vollständiger Server-Hook |
| `/docs/security.md` | 13 KB | Sicherheitsrichtlinie inkl. Vorfallshistorie |
| `/HANDOFF.md` | 24 KB | interner Übergabestand |
| `/tools/check-pb-rules.mjs` | 9,8 KB | Prüfwerkzeug inkl. Soll-Regelwerk |
| `/CHANGELOG.md` | 49 KB | Entwicklungschronik |
| `/debug.html` | 8,1 KB | Diagnoseseite |

Aus dem live abrufbaren `CLAUDE.md`, wörtlich:

```
| PocketBase Container (LIVE) | «PB-CONTAINER-LIVE» (Coolify-managed) |
| pb_hooks Pfad (LIVE)        | /var/lib/docker/volumes/«PB-HOOKS-VOLUME-LIVE»/_data/ |
| Server SSH Alias            | ssh «SERVER» |
| Admin-Login (App + PB UI)   | «SUPERADMIN-MAIL» |
```

Verzeichnis-Listing ist immerhin aus (`/docs/` → 403), aber jeder Dateiname ist aus dem
öffentlichen GitHub-Repo bekannt. Auf GitHub Pages dieselbe Lage.

**Warum es zählt.** Das ist kein abstraktes Risiko. Wer angreifen will, bekommt hier den
Bauplan gratis: welche Zugriffsregeln gelten, wo sie schon einmal falsch standen, wie das
Backend heißt, wie deployt wird, welche Adresse Superadmin ist. Das `CLAUDE.md` dokumentiert
jede je gefundene Lücke mitsamt Ausnutzungsweg — geschrieben, damit sie sich nicht wiederholt,
gelesen aber von jedem. Und es ist wörtlich das „einfach alles klauen", das nicht sein soll:
nicht der Code aus dem Browser, sondern die interne Dokumentation eines Produktivsystems.

**Empfehlung.** Ausliefern soll nur, was die App braucht: die vier HTML-Seiten, `js/`,
`assets/`, `styles.css`, `theme.css`, `favicon.svg`, `sw.js`, `docs/guide-*.html`. Zwei
gangbare Wege — der zweite ist der bessere:

- *Schnell:* nginx-Regeln, die `*.md`, `.pb_hooks/`, `tools/`, `tests/`, `supabase/`,
  `pocketbase/`, `debug.html` mit 404 beantworten. Braucht den Admin. Nachteil: eine neue
  Datei im Repo ist standardmäßig wieder öffentlich.
- *Sauber:* ein Deploy-Schritt, der nur die Auslieferungsdateien in den Container kopiert.
  Dann ist „öffentlich" eine bewusste Entscheidung statt der Voreinstellung.

**Aufwand.** Variante 1: eine halbe Stunde Admin. Variante 2: ein halber Tag, dafür dauerhaft.

**Sofort und ohne Admin möglich:** `debug.html` löschen (siehe S-2).

### K-2 · Jedes angemeldete Konto liest den gesamten Personendatenbestand

**Was ist.** Bestätigt aus dem Soll-Regelwerk (`tools/check-pb-rules.mjs:42-67`), und das
Werkzeug meldet für beide Instanzen „alle geprüften Regeln stehen richtig" — der Soll-Stand
**ist** also der Live-Stand:

```js
assignments:  listRule: '@request.auth.id != ""'   // jeder Angemeldete
              viewRule: '@request.auth.id != ""'
crew_members: listRule: '@request.auth.id != ""'
              viewRule: '@request.auth.id != ""'
```

Kein Bezug zur eigenen Person, kein Bezug zur eigenen Tour. Zwei HTTP-Aufrufe mit einem
gültigen Crew-Token genügen für:

- **alle Zuweisungen aller Touren** (laut Doku ~913 Datensätze) inklusive `crew_email`,
  `crew_name`, Datum, Position, Status — also den vollständigen Einsatzverlauf jeder Person;
- **alle `crew_members`** (23 Datensätze) inklusive der 10 echten Mailadressen, tourübergreifend
  plus globaler Pool.

Dieselbe offene Regel gilt nach dem Schema-Import-Stand auch für `email_log` (wer wann welche
Mail bekam) und `activity_log`. Beide stehen **nicht** im Soll-Regelwerk und werden daher von
`check-pb-rules.mjs` gar nicht überwacht.

**Warum es zählt.** Genau das ist „auf der Webseite alles abgreifen". Es braucht keine Lücke,
keinen Exploit — ein Konto genügt, und neun davon existieren. Ein verlorenes Handy, ein
wiederverwendetes Passwort, ein verärgertes ehemaliges Crew-Mitglied: in allen drei Fällen ist
der komplette Adressbestand weg. Das ist zugleich der Punkt, an dem es datenschutzrechtlich
ernst wird — es sind fremde Klarnamen und Kontaktdaten, und die Betroffenen haben sie dir
für die Tourplanung gegeben, nicht für die Einsicht aller anderen.

**Ehrlich zur Ursache:** Das ist kein Schlamperei-Befund. Die Regel ist so weit offen, weil die
App es so braucht — `loadAllKnownCrew` (dataService.js) liest bewusst **alle** `crew_members`
ohne Plan-Filter, damit „Aus Crew-Pool wählen" funktioniert. Es ist derselbe Mechanismus, der
schon zweimal zu Befunden führte: *eine Oberfläche liest direkt aus einer Collection, und die
Regel wird so weit geöffnet, bis das geht.*

**Empfehlung.** Der Weg, der hier bereits zweimal funktioniert hat: Hook-Route statt offener
Collection.
- `GET /pool` (authentifiziert) → Name + Mail der Pool-Mitglieder für den Auswahl-Dialog,
  ersetzt `loadAllKnownCrew`.
- `GET /planassignments/{id}` (authentifiziert, prüft Zugehörigkeit) → Zuweisungen **einer**
  Tour, ohne `crew_email` für alle außer Owner/superadmin.
- Danach `assignments` und `crew_members` auf Owner/superadmin/eigene Person zusammenziehen.
- `email_log` und `activity_log` auf `superadmin` (sie werden nur in der Konsole gebraucht).
- `check-pb-rules.mjs` um beide Collections **und** eine angemeldete Gegenprobe erweitern —
  die Innensicht fehlt dem Werkzeug bisher komplett.

**Aufwand.** 1–2 Tage inklusive Tests und gestaffeltem Rollout. **Reihenfolge zwingend
Hook → Frontend → Regel**, und „Frontend" heißt das auf der jeweiligen Umgebung
*ausgelieferte* JS (die Lehre aus dem v4.16-Rollout, CLAUDE.md).

### K-3 · Ein Crew-Konto kann sich selbst Zugriff auf fremde Touren verschaffen

**Was ist.** `crew_members` hat keine Beschränkung für `create`/`update`/`delete` — im
Schema-Import-Stand durchgehend `@request.auth.id != ""`, und das Soll-Regelwerk lässt diese
drei Regeln ungeprüft (`check-pb-rules.mjs:64-67` führt nur `listRule` und `viewRule`).

Die Hook-Route `/myplan/{id}` (main.pb.js:636-644) entscheidet über Zugriff so:

```js
var m = $app.findFirstRecordByFilter('crew_members',
  'plan_id = {:p} && email = {:m}', { p: planId, m: mail });
darf = !!m;
```

Zugriff hängt also allein daran, dass ein `crew_members`-Datensatz mit der eigenen Adresse und
der gewünschten `plan_id` existiert — **und genau den darf jeder Angemeldete selbst anlegen.**
Da `plans.listRule` inzwischen nur noch Owner/superadmin durchlässt, sind Plan-IDs zwar nicht
mehr auflistbar; über K-2 (alle `assignments` lesbar, Feld `plan_id`) sind sie aber trivial zu
beschaffen.

Dieselbe offene Regel erlaubt zusätzlich, **fremde `crew_members`-Datensätze zu ändern oder zu
löschen** — also Crew-Mitglieder aus Touren zu entfernen oder umzubenennen.

**Warum es zählt.** Das ist Rechteausweitung: aus „ich sehe meine Tour" wird „ich sehe jede
Tour", per Selbstbedienung, in einem einzigen POST. Zusammen mit K-2 ist ein beliebiges
Crew-Konto damit faktisch so mächtig wie ein Planer — nur ohne Schreibrechte am Plan selbst.

**Einschränkung, die ich offenlegen muss:** Ohne Superuser-Zugang konnte ich diese drei Regeln
nicht direkt am Server ablesen — anders als bei K-2, wo das Prüfwerkzeug den Abgleich liefert.
Belegt sind: der dokumentierte Regel-Stand, die fehlende Überwachung, und der Code der Route,
der auf `crew_members` vertraut. **Ein einziger authentifizierter Aufruf klärt es**; ich würde
das vor der Priorisierung machen.

**Empfehlung.**
```
createRule: @request.auth.role = "superadmin" || (@collection.plans.id ?= plan_id && @collection.plans.owner ?= @request.auth.id)
updateRule: dieselbe Regel
deleteRule: dieselbe Regel
```
Damit legt nur der Tour-Eigentümer (oder superadmin) Crew an — genau wie es die Konsole ohnehin
tut. Anschließend alle drei ins Soll-Regelwerk aufnehmen, sonst fällt es beim nächsten
Coolify-Redeploy still zurück.

⚠️ Vor dem Scharfschalten prüfen, ob `saveCrewLink` (dataService.js:615) je aus einem
Crew-Konto heraus läuft — sonst passiert dasselbe wie beinahe beim v4.16-Rollout.

**Aufwand.** Prüfung 10 Minuten, Umsetzung eine Stunde. **Das beste Verhältnis von Wirkung zu
Aufwand im ganzen Bericht.**

## Wichtig

### W-1 · Die Lizenz gehört einer fremden Firma und verschenkt deinen Code

`LICENSE`, Zeile 1–3:

```
MIT License

Copyright (c) 2021 Supabase, Inc. and contributors
```

Ein Vorlagen-Überbleibsel aus der Frühzeit des Projekts (das `supabase/`-Verzeichnis stammt aus
derselben Zeit, siehe S-1). Wirkung: In einem öffentlichen Repo ist das die maßgebliche
Rechtsangabe — Crewplaner steht damit unter MIT, und MIT erlaubt jedem ausdrücklich, den Code
zu kopieren, zu verändern und **kommerziell zu betreiben**. Dein Name kommt darin nicht vor.

Das ist das genaue Gegenteil deines Ziels. Und es ist der einzige Aspekt von „Codeklau", bei
dem eine Textdatei tatsächlich etwas bewirkt.

**Empfehlung.** Entscheide, was gelten soll:
- **Kein Nutzungsrecht** (mein Vorschlag, wenn es dein Produkt bleiben soll): `LICENSE` ersetzen
  durch „Copyright (c) 2026 Marco Hoch. Alle Rechte vorbehalten." Ohne Lizenz darf niemand
  legal kopieren — das ist der Normalfall des Urheberrechts.
- **Offen bleiben:** MIT behalten, aber der Copyright-Zeile deinen Namen geben.

Dass die alte Fassung im Git-Verlauf steht, ändert daran nichts Praktisches — maßgeblich ist
die aktuelle. **Aufwand: 5 Minuten.** Rechtsberatung ist das keine; im Zweifel jemanden fragen,
der das darf.

### W-2 · Kein einziger Sicherheits-Header am Live-Frontend

```
$ curl -sI https://crewplanner.nyxlightwork.de/
server: nginx/1.31.3
```

Das ist alles. Kein `Content-Security-Policy`, kein `Strict-Transport-Security`, kein
`X-Frame-Options`, kein `X-Content-Type-Options`, kein `Referrer-Policy`. Die API setzt immerhin
zwei davon (`nosniff`, `SAMEORIGIN`) — das Frontend, wo der Browser den Code ausführt und das
Token liegt, keinen.

Besonders CSP fehlt schmerzhaft: Zusammen mit W-4 (Token in `localStorage`) und W-5 (zwei
Stellen ohne `esc()`) hätte eine XSS-Lücke freie Bahn — kein Mechanismus würde den Abfluss des
Tokens zu einem fremden Server bremsen.

**Empfehlung.** In derselben nginx-Konfiguration wie K-1: `Strict-Transport-Security`,
`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`.
CSP zuletzt und vorsichtig — die App nutzt reichlich Inline-Handler (`onclick=`) und
Inline-`<style>`, eine strenge Richtlinie legt sie sofort lahm. Realistischer Einstieg:
`default-src 'self'; connect-src 'self' https://api.crewplanner.nyxlightwork.de;
img-src 'self' data:; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'`.
Das `unsafe-inline` ist ein Kompromiss, aber `connect-src` allein verhindert schon den
Datenabfluss zu fremden Zielen. **Aufwand: eine Stunde Admin + Test.**

### W-3 · Kein Rate-Limiting am Login

Zwölf Fehlversuche in Folge gegen `/api/collections/users/auth-with-password`, alle
gleichförmig mit `400` beantwortet, keine Verzögerung, keine Sperre:

```
400 400 400 400 400 400 400 400 400 400 400 400
```

Damit ist Passwort-Raten praktisch unbegrenzt möglich. Erschwerend: die Konten sind bekannt —
neun Adressen stehen namentlich im live abrufbaren `CLAUDE.md` (K-1). Ein Angreifer muss also
nicht einmal raten, wen er angreift, und `«SUPERADMIN-MAIL»` ist dort als Superadmin markiert.
Die Nutzer haben ihre Passwörter selbst gewählt; über deren Güte weiß niemand etwas.

Auch `/viewplan/{token}` ist ungedrosselt (30 Versuche, keine Bremse) — dort praktisch
unkritisch, weil die Tokens lang und zufällig sind.

**Empfehlung.** Traefik-Middleware `rateLimit` auf die Auth-Pfade (der Admin kennt den Weg über
`pocketbase-fix.yaml`); PocketBase bringt teils eigene Drosselung mit, die geprüft und
aktiviert werden sollte. Unabhängig davon: **die Login-Adressen aus der öffentlichen
Auslieferung nehmen** — das erledigt K-1 mit. **Aufwand: eine Stunde Admin.**

### W-4 · Anmelde-Token liegt in `localStorage`

Sechs Stellen lesen/schreiben `pb_token` dort (`pb.js:8`, `dataService.js:16`,
`auth-bootstrap.js:32/70`, `pb-login-bundle.js:13`, `authService.js:16`). Für JavaScript
frei zugänglich — jede XSS-Lücke ist damit gleichbedeutend mit Kontoübernahme, und beim
Superadmin-Konto heißt das: alles.

**Einordnung, ehrlich:** Die saubere Lösung wären `HttpOnly`-Cookies, aber PocketBase arbeitet
token-basiert; ein Umbau ist groß und riskant. **Deshalb rate ich davon ab** und empfehle
stattdessen, die *Voraussetzung* zu beseitigen: CSP (W-2) und `esc()`-Disziplin (W-5). Der
Befund steht hier, damit die Abhängigkeit dokumentiert ist — nicht als Aufgabe.

### W-5 · Zwei Stellen in `render.js` schreiben Namen ungeschützt ins HTML

`js/render.js`, drei Interpolationen ohne `esc()`:

```js
:91  `<th class="pos-h" ... onclick="openPosMenu(event,${i})">${p.short} <span ...>▼</span></th>`
:92  `<th class="pos-h">${p.short}</th>`
:108 `... <span style="...">${def}</span>` // defaultCrew-Name
```

Auffällig, weil dieselbe Datei 14 Zeilen weiter das Gegenteil festhält (`render.js:151`):

> „Crew-/Positionsnamen dürfen NIE ungeschützt in innerHTML, siehe v0.23.3-Härtung."

Alle anderen Ausgabestellen (`:184-204`, `crew.js`, `admin.html`) halten sich daran. Zeile 92
ist zudem in der **öffentlichen Booker-Ansicht** aktiv (`view.html` nutzt dasselbe `render.js`).

**Einordnung.** Beide Werte stammen aus `plan_data`, das nur der Tour-Eigentümer schreibt — die
akute Ausnutzbarkeit ist also gering, man müsste sich selbst angreifen. Zwei Gründe, es trotzdem
zu beheben: Erstens bricht ein Name mit `<` oder `"` die Darstellung — exakt der Fehler, den
v0.23.3 behoben hat, hier übersehen. Zweitens ist es eine gestellte Falle: Sobald irgendein
künftiger Weg einem Nicht-Eigentümer erlaubt, einen Positions- oder Standard-Crew-Namen zu
setzen, wird daraus gespeichertes XSS — und K-3 zeigt, wie schnell so ein Weg entsteht.

**Empfehlung.** `esc()` an allen drei Stellen. **Aufwand: 10 Minuten**, plus ein Guard, der
`render.js` auf uneskapierte Interpolationen prüft.

### W-6 · Der CORS-Guard merkt nicht, wenn CORS abgeschaltet wird

**Mutationstest, durchgeführt und zurückgenommen.** Ich habe die CORS-Prüfung im Hook
vollständig stillgelegt:

```js
if (false && !oeffentlich && origin) {   // Bedingung neutralisiert
```

Ergebnis: **`132 passed · 0 failed`** — alle Tests blieben grün, auch `tests/cors.test.mjs`.

Zur Gegenprobe die zweite Mutation, `view_token` in die `/viewplan`-Antwort geschmuggelt:
**`✗ Hook: /viewplan-Route gibt weder Token noch Owner heraus` — 131 passed · 1 failed.**
Dieser Guard funktioniert also, der CORS-Guard nicht. Beide Änderungen wurden zurückgenommen,
`diff` gegen das Original ist leer, 132 grün.

**Warum es zählt.** `tests/cors.test.mjs` wurde nach dem v4.17-Debakel geschrieben, um genau
das zu verhindern: eine CORS-Middleware, die geladen wird, aber nichts tut. Der Guard prüft die
*Reihenfolge* (Header vor `e.next()`) — nicht, ob der Block überhaupt erreichbar ist. Damit
wiederholt er auf Testebene denselben Denkfehler, den er auf Hook-Ebene abfangen soll: Er
belegt, dass Code *dasteht*, nicht dass er *wirkt*.

**Empfehlung.** Den Guard um die Prüfung ergänzen, dass die Bedingung nicht konstant-falsch ist.
Ehrlicher wäre allerdings eine echte Messung: `check-pb-rules.mjs` prüft CORS bereits gegen das
laufende Backend — dieser Weg trägt weiter als jede Textanalyse. Als Regel fürs Projekt:
**Ein Guard gilt erst als wirksam, wenn eine Mutation ihn rot gemacht hat.** Das ist in diesem
Projekt zwar oft dokumentiert, hier aber unterblieben. **Aufwand: eine Stunde.**

## Kosmetisch

### S-1 · `supabase/` — Altlast eines anderen Backends
`supabase/functions`, `supabase/migrations`, `supabase/schema.sql`. Das Projekt läuft seit
Langem auf PocketBase. Ursprung derselben Vorlage, aus der auch die falsche Lizenz stammt (W-1).
Löschen.

### S-2 · `debug.html` liegt live
`https://crewplanner.nyxlightwork.de/debug.html` → `200`. Laut Changelog eine
Diagnoseseite aus der Bounce-Zeit (v0.9.26), die Konsolenausgaben, Weiterleitungen und
Storage-Zugriffe mitschneidet. Auf einem Produktivsystem hat sie nichts verloren. Löschen —
das geht ohne Admin und nimmt einen Teil von K-1 sofort weg.

### S-3 · `love_invite`-Rest im Hook
Der Mailtyp wurde in v0.22.0 im Frontend entfernt, im Hook steht der Zweig noch. Toter Pfad,
der bei jedem Lesen des Hooks Aufmerksamkeit kostet. Entfernen.

### S-4 · `pickApiUrl` viermal dupliziert
Die Backend-Auswahl steht in `js/pure.js` (getestet) und als Inline-Kopie in `index.html`,
`admin.html`, `login.html` sowie `js/pb-login-bundle.js`. Nachvollziehbar begründet — die
Inline-Skripte laufen vor den Modulen. Aber vier Kopien einer Sicherheitsentscheidung
(„im Zweifel Test") sind vier Gelegenheiten für Abweichung. Ein Guard, der prüft, dass alle
vier Kopien dieselben Hostnamen führen, kostet wenig und schließt die Klasse.

### S-5 · `pocketbase/pb_schema.json` ist unbenutzbar
Laut `CLAUDE.md` enthält es veraltete Relation-IDs und darf nicht importiert werden — das
brauchbare Schema steht als JSON-Block im `CLAUDE.md`. Eine Datei, die aussieht wie das, was
man im Notfall braucht, es aber nicht ist, ist gefährlicher als keine. Entweder korrigieren
oder löschen.

## Codestruktur

Kein einzelner Befund, sondern die Lage — mit einer klaren Empfehlung.

**`admin.html` ist der größte blinde Fleck des Projekts.** 91 KB, davon **1127 Zeilen
Inline-JavaScript mit rund 60 Funktionen**. Alles außerhalb des Modulgraphen und damit von
**keinem** der 132 Tests erfasst — weder von den Guards für Erreichbarkeit noch für Importe.
Genau dort liegen aber die heikelsten Abläufe: `sendAdminInvite`, `openAdminCancellation`,
`saveDirectoryEntry`, `createPoolMember`. Der Changelog spiegelt das: v0.18.2, v0.23.1, v0.23.2,
v0.23.4, v0.29.3 sind allesamt Fehler in dieser Datei, jeder erst im Betrieb aufgefallen.

**Empfehlung**, und bewusst nicht „alles herauslösen": schrittweise, beginnend mit den
Funktionen, die Daten schreiben oder Mails auslösen. Jede Funktion, die nach `js/admin/*.js`
wandert, wird automatisch von den bestehenden Guards erfasst — der Nutzen tritt sofort ein,
ohne dass die ganze Datei angefasst werden muss. Ein Abend pro Gruppe.

**Die großen Module** (`userView.js` 979, `dataService.js` 664, `pdf.js` 451) sind
Aufteilungskandidaten, aber unkritisch: sie sind getestet, und `bulkStatus.js` zeigt, dass die
Trennung bei Bedarf sauber gelingt. Kein Handlungsdruck.

**Der Modulzyklus** `render ↔ userView` ist entschärft: `userView.js` importiert `render.js`,
umgekehrt gibt es keinen statischen Import mehr. Die in v0.12.1 dokumentierte Duldung ist
damit gegenstandslos — der Zyklus ist weg.

**Fehlerbehandlung** ist besser als der Changelog vermuten lässt. Die 17 leeren `catch`-Blöcke
umschließen ausnahmslos `localStorage`-Zugriffe (Privatmodus, Speicher voll) — dort ist
Schlucken richtig. Kein verschluckter `catch` auf einem Datenpfad gefunden. Kein fehlendes
`await` an den kritischen Schreibfunktionen. Das ist gepflegter Code.

**Logik.** Die Stellen, an denen das Projekt wiederholt gestolpert ist — Zeitzonen,
`getVal`-Auflösung, Statusübergänge, Update-Queue — sind heute jeweils durch einen eigenen
Guard abgedeckt, und die Tests laufen unter `TZ=UTC` wie `Europe/Berlin`. Ich habe hier keinen
Logikfehler gefunden. Der einzige offene Punkt ist die Guard-Blindheit aus W-6: die Guards
existieren, aber nur einer von zweien, die ich mutationsgeprüft habe, hat gehalten. Vor Verlass
auf die übrigen wäre ein Durchgang sinnvoll.

**Nebenbeobachtung**, nicht verfolgt: Der Import-Guard hat laut Changelog eine bekannte Lücke
bei verschachtelten Template-Literalen — potenziell auch als *falsch-negativ*. Das passt in
dasselbe Bild wie W-6.
